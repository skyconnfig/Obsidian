## 1. IIS 高并发与性能调优

### 1.1 突破 10 万并发的四板斧

经验来自多次比赛现场的并发压力实践，按生效优先级排列：

1. **调整应用程序池队列长度**：`queueLength` 从默认 1000 改为 65535（或 用户数 × 1.5）。注意这是针对**每个应用池**的设置，PowerShell 批量执行：
   ```powershell
   & $env:windir\system32\inetsrv\appcmd.exe set apppool "/apppool.name:$pool" /queueLength:65535
   ```
2. **appConcurrentRequestLimit**：系统级配置，放开 IIS 并发请求上限。CMD 运行：
   ```
   appcmd set config /section:serverRuntime /appConcurrentRequestLimit:100000
   ```
3. **修改 machine.config 的 processModel RequestQueueLimit**：将 ASP.NET 请求队列上限从默认值改为 100000。路径（注意 .NET 版本）：
   ```
   %systemroot%\Microsoft.Net\Framework64\v4.0.30319\CONFIG\machine.config
   ```
   将 `<processModel autoConfig="true" />` 替换为 `<processModel enable="true" requestQueueLimit="100000" />`
4. **注册表 MaxConnections**：TCP 连接数上限，默认值极保守，需要放大：
   ```
   reg add HKLM\System\CurrentControlSet\Services\HTTP\Parameters /v MaxConnections /t REG_DWORD /d 100000
   ```

**经验判断**：比赛当天若有 503 错误，优先检查队列长度和 appConcurrentRequestLimit。注册表和 machine.config 改动需要重启，只能提前做。

### 1.2 生产环境性能常规配置

- **禁用 IIS 日志记录**或只记录关键字段——日志写入是磁盘 IO 杀手
- **禁用 ASP 调试**：启用客户端调试和服务器端调试都设为 False
- **调整 ASP 每处理器线程数限制**：默认 25，建议提至 100（前提是了解应用的同步/异步模型）
- **调整 ASP 队列长度**：与线程数 1:1 起步，观察峰值后微调
- **启用 HTTP 压缩**（gzip）减少带宽，静态资源效果明显

### 1.3 常见 IIS 故障模式

| 现象 | 排查方向 | 解决 |
|------|----------|------|
| 500.19 配置错误 | web.config 被锁定或权限不足 | `appcmd unlock config -section:system.webServer/handlers` 或给文件夹加 Everyone 读权限 |
| 500.21 处理程序错误 | ASP.NET 未注册到 IIS | `aspnet_regiis.exe -i`（注意 64 位路径是 Framework64） |
| 500.30 应用池失败 | .NET 版本不匹配或依赖缺失 | 在应用池高级设置中确认 .NET CLR 版本 |
| 应用池自动停止 | 快速故障保护触发 | 将 `rapidFailProtection.maxCrashes` 设为 65530 |

## 2. SQL Server 数据库运维

### 2.1 内存占用过高

SQL Server 默认会吃掉几乎所有可用内存（设计如此），实际处理路线：

1. **打补丁最有效**：升级 SP3 能解决 SP2 下自动统计功能导致的内存泄漏
2. **手动限制**：在 SQL Server Management Studio 的服务器属性 → 内存中设置最大服务器内存。典型值是物理内存的 70-80%，留一些给 OS 和 IIS
3. **排查泄漏进程**：`sc config [服务名] type= own` 将可疑服务分离到独立进程，逐个观察

### 2.2 数据库误删恢复

这是生产事故的标准应对流程（有云快照为前提）：

1. 查看服务器是否有误删前的快照，确认最近时间点
2. 对当前盘符**做新快照**，然后还原到有数据的快照
3. 启动后复制目标数据库文件（.mdf + .ldf）到其他数据盘
4. 将云盘快照恢复到最开始状态（即还原前的状态）
5. **重新附加数据库 + 修改 web.config 连接字符串**

**关键教训**：云盘快照是数据库误删的终极救命稻草。没有快照的前提下，可以用 DiskGenius 等工具尝试文件级恢复。

### 2.3 站点数查询与数据库容量

文档中积累了大量的实用 SQL：

```sql
-- 查询所有数据库大小
SELECT
    database_name = DB_NAME(database_id),
    log_size_mb = CAST(SUM(CASE WHEN type_desc = 'LOG' THEN size END) * 8 / 1024.0 AS DECIMAL(10,2)),
    row_size_mb = CAST(SUM(CASE WHEN type_desc = 'ROWS' THEN size END) * 8 / 1024.0 AS DECIMAL(10,2)),
    total_size_mb = CAST(SUM(size) * 8 / 1024.0 AS DECIMAL(10,2))
FROM sys.master_files
GROUP BY database_id
ORDER BY total_size_mb DESC
```

### 2.4 数据清理通用模式

比赛系统的数据清理有统一套路——按时间戳删除业务表数据。核心模式：

```sql
-- 先 SELECT 确认记录数，再 DELETE
SELECT COUNT(*) FROM 表名 WHERE AddTime < '截止时间'
DELETE 表名 WHERE Operator != 2 AND AddTime < '截止时间'
```

清理方向：
- 按 `AddTime`、`PT_AddTime` 等时间字段分批删除
- 保留 `Operator=2` 的管理员配置数据
- 注意关联表（外键约束）的清理顺序：先子表后父表
- 批量清理后务必执行**收缩数据库**：`DBCC SHRINKDATABASE (数据库名)`

### 2.5 数据库批量备份（比赛前必备）

```sql
-- 生成所有用户数据库的备份命令
SELECT 'BACKUP DATABASE [' + name + '] TO DISK = N''D:\Backup\' + name + '_' + CONVERT(VARCHAR, GETDATE(), 112) + '.bak'' WITH INIT'
FROM sys.databases
WHERE database_id > 4  -- 排除系统库
```

## 3. 比赛/考试系统实施经验

### 3.1 比赛日检查清单（防止现场翻车）

赛前务必逐项确认：

1. **考核题目**：综合柜员设置为 7200s（2小时），确认 time 配置正确
2. **题目激活状态**：
   - 大堂经理和综合柜员：需要在管理员端和教师端**都激活**
   - 理财经理和客户经理：检查对公/个人分别激活
3. **实时成绩**：检查显示是否正常，控制网点绑定是否正确
4. **案例 ID 和考核 ID**：确认考场绑定关系
5. **硬件准备**：大堂经理配耳机，理财经理配德州计算器
6. **考点环境**：鼠标、键盘、Excel 或 WPS、计算器都逐台试过
7. **账号信封**：打印正式账号，剪裁封装后交给裁判长
8. **题目封装**：准备 A/B/C 三套题，由裁判长现场抽签

### 3.2 线下比赛常遇问题

从文档中整理的典型赛题反馈：

- **延时难操作**：比赛缺单人加时控件，仲裁长经常提出。建议考场备一个脚本或手工改数据库的考时字段
- **双热备缺失**：省级比赛没有成熟的方案验证过，需要提前准备备用服务器 + 数据库同步方案
- **实时成绩暴露**：备用代表队可以通过修改 `indexr2.html` 配置隐藏显示
- **大堂经理时长不均**：大堂经理默认很难达到 2 小时考试时长，和其余三岗明显不一致
- **题目反复修改**：赛前高频修改是常态，建议研究院推版本冻结机制。现场运维要有快速修改部署的能力
- **一键开题**：多次被提，可以考虑批量激活脚本减少重复操作

### 3.3 成绩导出与核对

比赛完毕后的标准操作：

1. 现场导出成绩（按四项业务分别导出）
2. 核对四项成绩，确认总成绩无误
3. 提交给裁判长，等公示
4. 拍照给区域经理，确认无异议再撤场

## 4. Nginx 网络配置

### 4.1 内网映射外网

核心模式：一台公网服务器做 Nginx 反向代理，将外部请求转发到内网服务器。

```nginx
server {
    listen 443 ssl;
    server_name ai.dianyueyun.com;

    ssl_certificate     cert/STAR.dianyueyun.com.crt;
    ssl_certificate_key cert/STAR.dianyueyun.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    location / {
        proxy_pass http://内网IP:端口;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

**配置要点**：
- `client_max_body_size 200M` 避免文件上传被截断
- `keepalive_timeout 650` 匹配长连接场景
- `worker_connections` 根据预期并发调整（文档中常用 10240）
- 证书使用通配符 `*.dianyueyun.com` 统一管理

### 4.2 HTTPS 局域网证书

使用 `mkcert` 工具生成本地可信 SSL 证书，解决局域网 HTTPS 访问：

```
mkcert -install
mkcert 内网IP或域名
```

然后安装到 IIS 的服务器证书中。注意需要将自签 CA 证书添加到客户端的受信任根证书颁发机构。

### 4.3 IP 受限与安全组

- 3389 远程端口是攻击高频目标，**务必修改默认端口**（注册表两个位置一起改）
- 内部服务（MySQL 3306、Redis 6379）不要对公网开放
- 使用云安全组只放通业务协议和端口

## 5. 安全防护与漏洞修复

### 5.1 勒索病毒防御

- **修改 RDP 端口**（默认 3389）：注册表 `HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp\PortNumber` 和 `HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server\Wds\rdpwd\Tds\tcp\PortNumber` 两处都要改
- 开启系统防火墙，阻止 445 端口入站
- 密码策略：12-16 位含大小写+数字+特殊字符
- 勒索软件解密资源：360 勒索病毒搜索引擎、腾讯哈勃专杀、火绒解密工具集、nomoreransom.org

**被加密后的处理优先级**：重装系统 + 设复杂密码 + 安全组限制 → 从本地备份恢复业务。不要盲目付费。

### 5.2 源代码泄漏

文档中记录的真实案例——`bin.rar` 备份文件直接放在 Web 可访问目录下，导致整个源代码可下载。

**修复**：将备份文件转移到非 Web 目录或直接删除。Web 目录下的 .rar、.zip、.bak 文件都是潜在的风险入口。

### 5.3 安全响应头（批量修复）

Powershell 脚本为所有 IIS 站点添加安全响应头：

```powershell
$HeadersToAdd = @(
    @{ name = "X-Content-Type-Options"; value = "nosniff" },
    @{ name = "X-Frame-Options";         value = "DENY" },
    @{ name = "X-XSS-Protection";        value = "1; mode=block" }
)

Get-Website | ForEach-Object {
    foreach ($h in $HeadersToAdd) {
        Add-WebConfigurationProperty -PSPath "MACHINE/WEBROOT/APPHOST/$($_.Name)" `
            -Filter "system.webServer/httpProtocol/customHeaders" `
            -Name "." -Value @{name=$h.name; value=$h.value}
    }
}
```

### 5.4 Tomcat 加固

Tomcat 的常规安全操作：
- 升级到最新安全版本（如 9.0.94+）
- 禁用默认应用和 AJP 连接器
- 配置目录列表禁用
- 限制 8080 端口访问源

## 6. 各类平台部署要点

### 6.1 .NET 平台应用的依赖陷阱

几乎所有部署问题的根源：
- **VS 2008/2010 先于 IIS 安装**：导致 ASP.NET 未注册到 IIS。修复：`aspnet_regiis.exe -i`（走 Framework64 路径）
- **IIS 安装时未勾选 ASP.NET**：500.21 错误的常见原因
- **VC++ Redistributable 缺失**：MySQL、Python 组件等依赖 VC++ 运行库，常见报错 `VCRUNTIME140_1.dll` 找不到

### 6.2 量化投资部署

部署 Python 量化投资系统的目录结构：
```
├── Web 项目（IIS 站点）
├── 数据库（SQL Server 还原）
├── Python 服务（量化计算引擎）
└── 配置文件（数据库连接字符串）
```

注意点：
- ASP.NET CORE 需要单独安装 Runtime
- 需要配置 Windows 防火墙开放对应端口
- 数据库定时备份脚本是标配

### 6.3 Windows 服务自启动

两种有效方式：
- **启动文件夹**：`shell:startup`（当前用户）或 `shell:common startup`（所有用户）
- **任务计划程序**：更灵活，支持延迟启动、失败重启、最高权限运行
