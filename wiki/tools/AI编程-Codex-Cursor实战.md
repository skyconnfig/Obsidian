## 1. Codex 三阶段开发工作流

这是从多次 Codex 完整开发项目中沉淀下来的核心方法论——**三个阶段迭代逼近**，而不是一次到位。

### 第一阶段：需求交互式梳理

Codex 的独特价值在于**能通过多轮对话将用户的碎片化想法结构化为可执行需求**。典型过程：

1. 用户给出一段自然语言描述的需求（往往是片段化的）
2. Codex 主动提问，识别缺漏，整合要点
3. 输出一份结构化的功能需求文档
4. 再逐步细化到前端 README、后端接口说明、技术方案

**实际案例——数据分析 Agent 前端需求的演变**：
- 最初：用户说"想要一个简易的数据分析 Agent"
- 经过多轮追问，Codex 梳理出：左侧 2/3 仪表盘 + 右侧 1/3 Data Chat 的布局
- 确定技术栈：Vue3 + ECharts + OpenAI API
- 最终生成完整的前端文档和后端技术方案

**关键经验**：不要跳过此阶段直接让 Codex 写代码。需求梳理得越清楚，开发阶段的返工越少。

### 第二阶段：功能迭代实现

这一阶段按"分层推进"的方式执行：

1. **先框架后细节**：布局结构 → 数据流 → 交互细节
2. **先 Mock 后真实数据**：先让页面跑起来，再接入后端
3. **分批提交**：每完成一个功能模块就验证一次

### 第三阶段：精修与样式调整

Codex 的典型精修提示词模式：

```
阶段一：调整前端风格样式
→ "采用深色主题，紫色渐变背景，玻璃态卡片效果"

阶段二：调整前端核心功能
→ "第一排：4 个 KPI 卡片横向排列，包含同比/环比变化"

阶段三：对前端样式和功能进行精修
→ "红字上涨，绿字下降，同比/环比用白色字"
```

## 2. Cursor 全栈开发最佳实践

从文档中提炼的 9 步最佳实践流程：

### 2.1 工作流

```
ChatGPT 规划 → Bolt.new 设计 UI → Cursor 开发功能
```

**不要用 V0**——从实际体验看，Bolt.new 在 UI 生成效果上远优于 V0。V0 + Cursor 可能需要一天的工作，Bolt.new + Cursor 一小时搞定。

### 2.2 项目文档组织

在 Cursor 中将关键文档保存为 `.md` 文件：
- PRD（产品需求文档）
- 数据库架构设计
- 用户旅程/流程图
- 后端接口功能说明
- 前端 README

这些 **.md 文件就是 Cursor 的上下文**——让 AI 始终能访问项目的完整信息。

### 2.3 官方文档管理

使用特定框架时，将官方文档同步到 Cursor 中。这样 AI 在生成代码时始终引用最新最准确的信息，减少幻觉和错误。

### 2.4 可重用代码片段

当 Cursor 生成高质量代码时，保存为 `.md` 文件中的可重用示例。这个习惯对后续项目是巨大的效率提升。

### 2.5 用模板起步

不要从零开始。使用样板代码处理认证、数据库、支付等通用功能。

## 3. Rules 文件体系

### 3.1 Cursorrules 管理

从最佳实践中提炼的 rules 文件结构：

| rules 文件 | 用途 | 示例内容 |
|-----------|------|----------|
| `common.mdc` | 全局代码规范 | 优先简单方案、避免重复代码、区分环境 |
| `code-work.mdc` | 开发行为规范 | 项目初始化结构、修改范围约束、测试要求 |
| `git-auto-commit.mdc` | 自动提交规范 | conventional commit 格式 |
| `springboot.rules` | 框架特定规则 | Spring Boot 代码风格 |
| `vue3.rules` | 框架特定规则 | Vue3 + Element Plus 规范 |

### 3.2 核心规则精选

来自 `最佳实现coursorules.md` 的实战规范：

```
- 始终优先选择简单方案
- 修改代码前，检查是否已存在相似功能
- 仅针对明确需求进行更改
- 修复问题时优先排查现有实现，避免引入新技术
- 文件超过 200-300 行时需重构封装
- 开发与生产环境严禁使用 Mock 数据
- 不触碰与任务无关的代码
- 为所有主要功能编写全面测试
```

### 3.3 5S/6A 个人开发规则体系

> 来源：`raw/clippings/其他/文档/完整 5S 规则以及6A.md`
> 一套自定的 AI 辅助开发行为准则，确保一致性和代码质量

#### 五大核心规范

| 规范 | 要求 | 关键约束 |
|------|------|---------|
| **1S 文档管理** | 新项目先建「说明文档.md」，含规划/实施/进度 | 每次重开项目先读更新 |
| **2S 开发流程** | 需求拆分为 ToDoList，顺序执行，逐项闭环 | 禁止跳步 / 同时改多文件 |
| **3S 问题解决** | 遇技术问题先查官方文档 | 严禁无脑复制粘贴 |
| **4S 执行约束** | 不延期、不超计划、不出错 | 三"绝不允许"原则 |
| **5S 环境统一** | 统一开发环境配置，避免跨系统问题 | |

#### 核心原则

1. **文档先行**：任何代码之前，必须有「说明文档.md」作为项目入口
2. **闭环执行**：每完成一个任务，同步更新文档 + 代码状态 + 提交信息
3. **官方优先**：技术问题优先查官方文档，其次可信社区，最后才是 AI 生成

> 这套规则与本篇 §1「三阶段开发工作流」深度互补——前者是方法论，后者是行为约束。

## 4. 复现项目方法论

这是一个经过验证的用 AI 复现现有项目的标准流程：

### 4.1 核心思路

```
原始项目 → AI 分析生成复现文档 → AI 按文档逐步复现
```

### 4.2 提示词模板

**第一步：拆解任务**
```
我希望通过提示词让 LLM 一步一步复现整个项目，请帮我进行任务拆解，
并撰写每一步复现项目的提示词。

要求：
- 文档位置：将复现过程写在 docs 目录中
- 不要给出代码：复现文档中不包含示例代码
- 始终给出测试方式：每个任务完成后给出可靠的测试方法
- 语言：始终用中文
```

**第二步：逐步实现**
```
我准备实现一个 xxx 项目，项目的具体细节和详细的实现步骤
都被我写在了 docs 目录中，请读取 docs 目录中的文档，
指导我一步一步完成整个项目。

你不必一次便完成整个项目的开发，而应该严格按照文档一步一步
进行开发，每次只执行一个具体步骤。
```

### 4.3 实际案例

复现 `Deep-Research-AI-Agent` 项目时，还应用了后续优化：
1. 将所有界面改为中文
2. 从仅支持 OpenAI 扩展到支持 DeepSeek、文心一言、阿里千问、Ollama、Dify、Coze

## 5. 反编译与 Java 修复

### 5.1 Java 反编译工具选择

| 工具 | 特点 | 最佳场景 |
|------|------|----------|
| **CFR Decompiler** | 命令行，反编译最准确 | 生成可编译源码 |
| **Recaf** | 图形界面，集成多种引擎 | 可视化操作、修改再打包 |
| **Procyon** | 命令行 | 少数情况下兼容性优于 CFR |
| **Bytecode Viewer** | 图形多功能 | 对比不同反编译结果 |

**推荐组合**：CFR 命令行批量处理 + Recaf 图形化微调

```bash
# CFR 批量反编译
java -jar cfr.jar yourfile.jar --outputdir ./src
# 批量处理多个 jar
for %f in (*.jar) do java -jar cfr.jar "%f" --outputdir "%~nf-src"
```

### 5.2 反编译后的修复模式

实际遇到过的问题：
1. **包声明错误**：反编译出的 `.java` 文件包路径不对 → 手动修正后创建标准 Maven 项目结构
2. **依赖缺失**：通过上下文推断缺失的库并添加 pom.xml 依赖
3. **使用 Codex 修复**：将反编译出的代码 + 错误信息给 Codex，让其自动生成修复后的 Maven 项目

## 6. 集成与调试经验

### 6.1 外部服务集成模式

将 AI 服务（TTS、SadTalker 等）集成到现有项目的通用套路：

```
1. 确认服务已启动（检查端口和访问地址）
2. 确认服务目录和文件结构
3. 让 Codex 分析现有项目结构
4. 给出集成指令："帮我集成到当前项目，可以根据实际情况自己合理调整"
5. 验证集成后的功能
```

### 6.2 常见问题修复

- **Codex 一直执行命令**：使用 `--ask-for-approval never --sandbox danger-full-access -c model_reasoning_effort=high` 配置
- **Codex VS Code 插件 Sign-in failed**：检查网络代理配置
- **无限续杯工具**：`go-cursor-help` 项目（yuaotian/go-cursor-help），支持 Cursor v0.44.11 及以下

## 7. 经验总结

### 7.1 AI 编程的五条核心原则

1. **文档先行**：在任何代码生成之前，先让 AI 生成完整的 .md 文档（PRD、架构、接口）
2. **分层推进**：从框架到细节，从 Mock 到真实数据，每层验证后再推进
3. **增量积累**：高质量的 AI 生成代码保存为可重用片段，形成个人代码库
4. **Rules 驱动**：用 cursorrules 文件约束 AI 的行为和风格，确保一致性
5. **复现优于重写**：先用 AI 复现已验证的项目，再在其基础上做定制

### 7.2 Codex vs Cursor 的定位差异

| 维度 | Codex | Cursor |
|------|-------|--------|
| 工作模式 | CLI 对话驱动 | IDE 内嵌 |
| 适合场景 | 复杂需求交互梳理、大规模重构 | 日常开发、UI 生成、快速迭代 |
| 上下文管理 | @文件引用、MCP 工具 | .cursorrules、.md 文档 |
| 优势 | 多轮对话深入、需求结构化能力强 | 编辑器集成、实时预览、续杯方法成熟 |

## 8. Codex 自我提升提示词工作流

> 来源：`raw/clippings/适用于Codex的自我提升提示词(prompt).md`
> 目标：让 Codex 回顾历史会话，发现重复性手动工作流并封装为可复用技能

### 8.1 核心思路

Codex 不只是帮你写代码的工具——它还能**帮你优化自己使用 Codex 的方式**。定期让 Codex 回顾过去的工作记录，识别重复模式，封装成技能或自动化流程，形成「使用工具的元能力」。

### 8.2 提示词模板

```
回顾我过去 30 天的工作记录（如果记录不足 30 天，则追溯至所有可用历史），
识别出那些值得封装的重复性手动工作流。
```

### 8.3 执行标准

仅当候选任务**同时满足**以下条件时才值得封装：

| 条件 | 说明 |
|------|------|
| ✅ 重复出现 | 至少出现过两次，或明显有高成本的重复倾向 |
| ✅ 输入稳定 | 具备可预期的输入格式 |
| ✅ 步骤可复现 | 存在清晰的操作步骤序列 |
| ✅ 输出明确 | 有明确的输出结果或终止条件 |
| ✅ 效益显著 | 封装后能提升速度、质量、一致性或可管理性 |

### 8.4 检查清单

1. **参考现有证据**：Codex 会话记录、记忆库、Chronicle 记录、已有技能
2. **审视工作范围**：编程、调研、写作、运营、数据分析等
3. **按标准筛选**：满足全部 5 项条件才封装
4. **增量实施**：每次封装一个技能，验证后再继续

### 8.5 与三阶段工作流的关系

这个工作流是第 1 节「三阶段开发工作流」的**元层面补充**——前者帮你完成项目，后者帮你优化完成项目的方式。建议每 2-4 周执行一次。

## 9. Codex 设计美学 — 三套技能包

> 来源：`Clippings/Post by @Saccc_c on X.md`
> 让 Codex 输出设计师级 UI 的三套实战技能

### 9.1 技能包速览

| 技能 | 核心能力 | 适用场景 |
|------|---------|---------|
| **impeccable** | 整体设计品质远超 uiuxpromax，实用性强 | 网页/App UI 设计美感提升 |
| **taste skill** | imagegen-frontend-web 生成设计参考图 + image-to-code 1:1 还原 | 从参考图到代码的完整体验 |
| **Frontend App Builder** | Codex 内置技能，链式流程：设计图 → 代码，颜色/图标强制对齐 | 工程化设计实现，含 shadcn/ui + 浏览器验证 |

### 9.2 推荐工作流

```
参考图收集 → taste skill 生成高质量设计稿
    → Frontend App Builder / image-to-code 还原为代码
    → impeccable 微调美学细节
```

> 与传统「写好代码再调样式」相反，这套流程是先定美学方向，再用 AI 逐层落地。

> 组合使用 = 社媒数据采集 + 反爬对抗 + 浏览器级操作，全在 Claude Code 内完成。
