# 银行业务培训考核系统产品需求文档（PRD）

## 1. 项目概述

### 1.1 项目背景

本系统旨在为银行业务培训提供全面的考核管理平台，包括手工点钞、翻打传票、字符录入等多种考核模式，满足银行业务培训和考核的需求。系统将帮助银行提高业务培训效率，标准化考核流程，为银行员工技能评估提供科学依据。

### 1.2 项目目标

- 建立完整的银行业务培训考核管理系统
- 支持多种考核模式和评分标准
- 提供全面的用户管理和数据分析功能
- 实现考核过程的自动化和标准化
- 提高培训考核效率，降低人工成本
- 为银行业务培训提供数据支持和决策依据

### 1.3 技术选型

- **前端**：ElementPlus UI（Vue）
- **后端**：ASP.NET
- **数据库**：SQL Server

## 2. 用户角色定义

系统支持四种用户角色，各自拥有不同的权限和功能：

| 角色 | 描述 | 主要功能 |
| --- | --- | --- |
| 管理员 | 系统最高权限用户 | 系统管理、考核设置、数据管理 |
| 老师 | 培训教师 | 查看学生成绩、分析考核数据 |
| 裁判员 | 考核评判人员 | 评分、成绩录入、考核监督 |
| 学生代表 | 参与考核的学员 | 参加考核、查看个人成绩 |

### 3.1 用户登录功能

#### 3.1.1 功能描述

用户可选择不同角色进行登录，系统根据角色提供相应的功能界面。

#### 3.1.2 功能需求

- 登录框包括用户名、密码输入框
  - 用户名：必填，长度4-20字符，仅允许字母数字
  - 密码：必填，长度8-20字符，需包含大小写字母和数字
- 角色选择（管理员、老师、裁判员、学生代表）
  - 默认选择学生代表
  - 管理员需二次验证
- 记住密码功能
  - 有效期7天
  - 仅在本设备有效
- 注册功能（新用户注册）
  - 需验证邮箱/手机号
  - 初始密码需强制修改
- 登录验证和权限控制
  - 5次失败锁定30分钟
  - 会话超时30分钟

#### 3.1.3 业务规则

1. 密码加密存储，使用PBKDF2算法
2. 权限控制基于RBAC模型
3. 登录日志记录IP、时间和设备信息

#### 3.1.4 界面原型

登录界面包含系统名称、Logo、登录表单等元素，设计简洁明了。

   - 管理员界面
   - 老师界面

   - 学生界面

   - 手工卷管理
   - 传票管理

   - 考核数据访问
   - 成绩数据访问

4. **数据库**：存储系统数据
   - 用户表
   - 学生表
   - 班级表
   - 手工卷设置表
   - 传票设置表
   - 考核任务表

1. **用户登录**：所有用户通过登录界面进入系统

   - 管理员进入系统管理界面

## 5. 数据库设计

### 5.1 数据关系图

系统数据库设计遵循以下关系：

- 用户表(USERS)与学生表(STUDENTS)是一对多关系
- 班级表(CLASSES)与学生表(STUDENTS)是一对多关系
- 用户表(USERS)与手工卷表(MANUAL_EXAMS)是一对多关系
- 用户表(USERS)与传票表(VOUCHER_EXAMS)是一对多关系
- 用户表(USERS)与考核任务表(ASSESSMENT_TASKS)是一对多关系
- 学生表(STUDENTS)与各类考核表是多对多关系

## 12. 非功能性需求

### 12.1 可用性

- **界面友好**：系统界面应简洁直观，易于理解和操作。
- **操作便捷**：常用功能应易于访问，减少用户操作步骤。
- **响应及时**：系统操作响应时间应满足性能要求，避免用户等待。
- **帮助文档**：提供在线帮助文档和操作指引。

### 12.2 可靠性

- **系统稳定**：系统应能长时间稳定运行，减少宕机时间。
- **数据一致性**：确保数据库操作的原子性、一致性、隔离性和持久性（ACID）。
- **容错能力**：系统应具备一定的容错能力，例如网络中断或服务器故障时能妥善处理。

### 12.3 可维护性

- **代码规范**：遵循统一的编码规范，提高代码可读性。
- **模块化设计**：系统采用模块化设计，便于功能扩展和维护。
- **日志记录**：完善的日志记录机制，便于问题排查和系统监控。
- **配置管理**：关键参数应可通过配置文件进行管理，避免硬编码。

### 12.4 可扩展性

- **架构设计**：系统架构应具备良好的扩展性，支持未来业务增长和功能增加。
- **接口设计**：提供标准化的API接口，便于与其他系统集成。

### 12.5 兼容性

- **浏览器兼容**：前端界面应兼容主流浏览器（Chrome, Firefox, Edge 最新版本）。
- **操作系统兼容**：后端服务应能在指定的服务器操作系统（如 Windows Server）上稳定运行。

## 13. 错误处理

### 13.1 错误分类

- **用户输入错误**：如格式错误、必填项未填等。
- **业务逻辑错误**：如权限不足、操作不符合业务规则等。
- **系统异常**：如数据库连接失败、服务器内部错误等。

### 13.2 处理机制

- **前端提示**：对于用户输入错误，应在前端界面给出明确、友好的错误提示。
- **后端校验**：后端应对所有输入进行严格校验，防止非法数据。
- **统一异常处理**：后端应建立统一的异常处理机制，捕获并记录系统异常。
- **错误日志**：所有未捕获的系统异常和关键业务错误都应记录到错误日志中，包含详细的错误信息和堆栈跟踪。
- **用户反馈**：对于系统异常，应向用户显示通用的错误提示信息，避免暴露敏感的系统内部细节。
